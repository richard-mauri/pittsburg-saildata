# Mauri's Weather & Water Conditions — architecture contract

This documents current boundaries and non-negotiable behavior, **not** a requirement to reorganize the sailing source like ScraperGo. Inspect actual code and call sites before modifying a contract.

## Runtime and component ownership

The root Go service includes `main.go` (routing/report preparation), `ui_templates.go` (the four embedded Go HTML template bindings), `web/templates/*.html` (browser UI HTML/CSS/JavaScript), `wind.go`, `currents.go`, and related sources. Go `embed.FS` includes the standalone templates in the compiled binary; the root `go.mod` requires at least Go 1.16. Do not confuse the root-owned `web/templates` with the separate `ui/` Go module. Build the full root package. The repository also contains `cmd/marineplacesgen.go`, supporting assets/scripts, and a separate `ui/go.mod` module. Root `go test ./...` does not automatically validate the nested module. Test it independently for changes in that module.

The public site at https://weather.themauris.org currently uses a locally running Go server exposed through the owner's Cloudflare Tunnel. Do not change listener/process ownership, launchers, private credentials, or tunnel behavior as an incidental code or theme change.

## Environmental data semantics

**Observed wind** comes from NOAA/NDBC and selected validated NOAA CO-OPS mappings. Show timestamps, source and freshness; station height/exposure matters. Existing documented fallback mappings include PSBC1 (9415115), MZXC1 (9415102), PPXC1 (9414847); do not double-count overlapping samples from different feeds. Automatic nearest-usable wind selection has a documented 30-minute freshness rule; check source before editing.

**Tidal currents** are NOAA **predictions**, not directly observed flow at the boat. Flood, ebb, slack, maxima and current-station selection remain distinct from wind observations and wind-station choice.

**Forecasts and overlays** (marine/point weather, wind barbs, radar, smoke/fire, pressure, temperature, swell and other layers) are separate products with differing coverage, timeliness and provenance. Never present one as another.

## Selection, UI and routes

Clicking a map point selects the sailing location. **Panning, zooming, or Center Map must not change that selected location.** Preserve automatic and explicitly overridden `station=` behavior, while current-station matching stays independent. Preserve Conditions Now and Planning and Details, history charts/tables, units, warnings, responsive layout, overlays, markers and popovers.

Existing documented routes include `/report`, `/planning`, `/wind-readings`, `/wind-stations`, `/point-weather`, `/marine-forecast`, and supported HTML/text/JSON output. The last documented `/wind-readings` fix expects JSON fields `hours`, `readings`, `summary` and windows 1, 4, 8, 12, 16, 20 or 24 hours. Trace handlers and front-end consumers before changing schemas.

## Homepage-authenticated automatic preferences (Issue #17)

The embedded `web/static/account.js` runs on Conditions Now and Planning and Details. SailingGo consumes Homepage's URL-fragment `#suite_token`, removes it immediately and retains the transferable bearer only in tab-scoped `sessionStorage`. Explicit `#suite_mode=local` clears it. Identity and expiry come from the trusted `/api/session/profile` bearer validation; no independent SailingGo login exists. The shared banner renders **Signed in as [verified user]** without an app or role suffix. Guest and preference-sync notices appear separately below the banner, with no manual Save/Load controls.

On authenticated startup, SailingGo GETs the revisioned `/api/storage/sailing` account record. Saved settings are applied automatically to the current view, including canonical URL parameters and map settings where the map exists. When an account has no record, its initial preferences are established without requiring a manual sync. Changes are staged in the tab before URL navigation and optimistically PUT with the last server revision; the next page also recovers staged changes if navigation canceled an earlier request. The previously loaded account record, not a stale launch URL or another user's local settings, is authoritative. Conflict (HTTP 409), invalid schema, expiry, loss of network or a new identity must not silently overwrite another account. A conflicting browser change is retained locally and identified in the account-status text. Browser-only visits retain a distinct local browser copy and remain functional.

The preference payload schema remains version 1, with selected URL settings, overlays, map type and marine-place categories. Panning/zooming the map does not become a selected sailing location. The merged Homepage companion provides the trusted origin, storage namespace and handoff; the owner controls Mac/Safari/live-tunnel acceptance for future changes.

## Direct-visit recovery (Issue #19)

On the public `weather.themauris.org` origin only, if the embedded account client has no cached bearer and was not explicitly launched with `#suite_mode=local`, it redirects once to Homepage's exact fixed `/launch/sailing` route. Homepage runs a same-origin POST against the existing parent session and returns only a child bearer in `#suite_token` or explicit `#suite_mode=local` when no valid session exists. SailingGo clears the fragment, retains bearer only in tab-scoped sessionStorage, and performs the same validated profile+revisioned account sync as normal handoff. Explicit browser-only mode suppresses recovery, avoiding redirect loops. A direct visit when Homepage's bridge has a network error stays on its recovery error page with a manual local-mode link; it does not forge sign-in. No changes to authenticated user isolation, session lifetime, automatic preference saves or NOAA/dashboard semantics. The companion Homepage direct-visit bridge is merged.

## Optional Homepage activity telemetry (Issue #21, merged; verified identity in Issue #23)

`activity.go` contains a strictly optional, server-only `ActivityReporter`. Environment variables `SAILING_ACTIVITY_URL` and `HOMEPAGE_ACTIVITY_KEY_SAILING` jointly enable it; if disabled, embedded templates receive no new `activity.js` reference. The existing `ui_templates.go` embedding pipeline inserts a defer-loaded script only when the private configuration validates. Browser-generated random tab IDs stay in same-origin tab `sessionStorage` and are submitted to SailingGo's own strict-origin `POST /api/activity/ping`. The reporter bounds presence to 5,000 entries, throttles repeated IDs and computes rolling windows in memory. A server-only no-redirect request submits aggregate data to Homepage `POST /api/admin/activity/ingest` as `sailing`, with an explicit service bearer, timestamp and nonce, once a minute. No coordinates, NOAA data, user IDs, station names or per-tab identifiers leave SailingGo.

Issue #23 adds server-side verification of the existing Homepage child bearer before marking activity signed in. The trusted Homepage profile endpoint returns origin-scoped pseudonymous session/user aliases, enabling per-session deduplication across tabs and private per-user presence summaries without putting aliases or bearers into collector reports. Rejected supplied identity gets a 401 response; Homepage verification outage gets 503. The embedded account client recognizes Homepage's one-hour `guest` role without attempting account storage, and shows a non-dismissible sign-in dialog with a manual Homepage action for invalid/expired/explicit local sessions. Named settings and URL/viewport rules are unchanged.

In `main.go`, server request middleware measures the concurrent lifetime of rendered reports and weather/map API requests, excluding health and static assets. `prefetchSwellRaw` separately increments the same in-flight count only once its bounded prefetch slot is acquired. This is a snapshot of observed work, not every upstream goroutine in the service. No changes are made to NOAA observation/prediction semantics, location/viewport separation, HTML/text/JSON response formats, authentication or page preferences. The optional `SAILING_ACTIVITY_TEST_LISTEN=127.0.0.1:8087` forces only an explicitly requested local test instance onto loopback; the existing production listener default is otherwise unchanged. Issue #23 implemented server-side Homepage verification of named/guest activity, with per-session deduplication; invalid bearer returns 401 and temporary verification outage 503.

## Homepage-verified suite access candidate — Issue #35 (not yet wired)

`sailing_suite_auth.go` stages an independent per-request verifier using the immutable-pinned Homepage `shared/auth` module already consumed by NewsGo and ScraperGo. NOAA observed wind, predicted tidal currents, map click versus pan and account preference isolation remain untouched.

## Explicit user-initiated preferences — draft PR #36

The earlier automatic 250 ms Homepage preference writer and 1.2 s retry timer in `web/static/account.js` are replaced with a single user-triggered `flush()` handler on the **Save Changes** button in the two report views. `stage()` writes a revision-scoped personal draft to the existing tab sessionStorage `sailing.preferences.pending-account.v2`; `stageGuest()` writes the Guest draft to `sailing.preferences.pending-guest.v1` (also tab sessionStorage). Neither stage function commits to Homepage or the browser's saved local preference record. Pending preferences are applied on navigation/restoration and only saved upon button activation. The Guest commit writes `sailing.preferences.browser.v2`, and the personal commit issues one revision-checked `PUT /api/storage/sailing`. Conflicts retain changes and block overwrite; other failures leave pending edits available for manual retry. A `beforeunload` prompt protects unsaved edits, excluding internal account-preference restore navigation which preserves the pending draft. Guest profile verification and per-user account isolation are unchanged. The common Homepage account record retains schema version 1 and the existing URL/map/overlay properties. The staged `SailingSuiteGate` remains unwired: this is persistence/UI work, not a claim of completed weather API authorization.

### Net-change detection and explicit discard — Build v429

The dashboard tracks `savedSnapshot`, a deep copy of the last successfully committed account/browser preferences. `same()` compares normalized preference maps regardless of object key insertion order. Each personal or Guest edit first checks `refreshDirty()`: if the new state equals the saved snapshot it removes its tab-scoped pending draft and clears the dirty flag, even if the user previously changed the map type or overlays. A shared `ui-button` **Discard Changes** control is installed alongside **Save Changes** on the two report views; it clears pending drafts and the blocked conflict state, then reapplies the saved snapshot. Discard issues no Homepage PUT and does not update Guest browser-local persistence. A successful Save replaces the snapshot; a failed/409 Save leaves the draft intact. The beforeunload warning depends on net unsaved differences, not the number of change events. This behavior does not change the still-unwired security gate, NOAA, or account ownership.

The real capture-handler regression includes visible checked and unchecked overlay/category controls and verifies Street → Nautical → Street, then an actual overlay toggle and reversal, for both personal and Guest sessions. ## Current server authorization boundary — Build v436 draft

The previously staged SailingSuiteGate is now wired into the production Go listener. main.go constructs NewSailingHTTPAuth(NewSailingSuiteGate()) and wraps the final router with authGate.ProtectWeather(handler) before http.ListenAndServe. The full router is default-deny, except the narrow public allowlist: health, welcome, activity.js, hero/tanner images and favicons. Report HTML/text/JSON, planning, wind, current, weather, all environmental overlays, marine-places JSON, API and unknown routes are protected. Each request verifies the authorized Homepage profile. Missing/revoked/expired identity is denied (401), and Homepage network/profile failures return 503. Spoofed identity headers and unverified local mode never authorize.

Since browser navigation cannot supply Authorization headers, anonymous top-level HTML requests receive a no-data, no-store entry page that consumes Homepage's suite_token fragment, erases it from the URL, and POSTs to /suite/session with same-origin verification. The server creates a first-party Secure HttpOnly SameSite=Lax __Host-sailing-session cookie containing an AES-GCM encrypted token plus expiry. The encryption key is generated at process startup; restart invalidates old cookies. Cookie-authenticated writes require same origin. The server still revalidates every weather/API request rather than trusting the cookie alone. Local loopback uses a separate non-Secure browser cookie name for development, but cannot bypass Homepage verification. An explicit Authorization Bearer header is also supported for CLI clients. AJAX chart refreshes receive 401 rather than a sign-in HTML body on authorization failures. User/admin and verified Guest are allowed for application use; Guest settings remain browser-local and Homepage isolates personal settings by user. Earlier notes about an unwired gate describe older builds, not v436. CI mocks are not real Safari or tunnel verification.

### Nautical chart tile response diagnostics — Issue #37 NEXT candidate

The user reported Nautical selected at zoom 11 with the ordinary Street Map visible and no notice. The pre-existing fallback only acted after a Leaflet `load` event containing zero successful tiles and at least one `tileerror`. A request that stalls without a final `load` or an HTTP 200 transparent chart tile could therefore leave no status. The browser cannot safely inspect NOAA cross-origin PNG pixels without explicit upstream CORS support; a successful WMS image response does **not** prove chart content. To address both cases without inventing a maintenance diagnosis, a Nautical `loading` cycle now starts a 12-second bounded response check, cancels it when leaving Nautical, and preserves the Street underlay. If no tile has arrived, it falls back to Street and shows a neutral **not responding / try again later** message. If one or more tiles arrived, it keeps the nautical layer and displays an **if details are missing** advisory, distinguishing uncertain visual content from confirmed request failure. This advisory may also appear over genuine chart imagery; it is deliberately conditional. The notice now wraps rather than truncating. No new NOAA HTTP proxy, CORS configuration, source switch, account write or autonomous retry has been added; user may reselect Nautical to retry. CI-only JavaScript tests simulate both events and timeouts; Safari/real upstream must still be accepted by the owner.

### Go NOAA WMS adapter and self-populating nautical tile cache (Issue #37)

The Leaflet Nautical layer is a single same-origin XYZ URL, `/api/charts/tiles/{z}/{x}/{y}.png`. `nautical_tiles.go` now implements a **disk-first, NOAA-second** handler behind SailingGo's existing mux/auth wrapper. Default persistent cache location is `filepath.Join(os.UserCacheDir(), "sailing-go", "nautical-tiles")` (if a user-cache directory is available); override with operator-managed `SAILING_NAUTICAL_TILE_DIR`. There is no additional server process. The cache is a collection of PNGs at XYZ `z/x/y.png`, **not a NOAA NCDS MBTiles database**. On cache hit, a validated PNG is returned without NOAA traffic. On cache miss, the Go server (not Safari) calls the pinned existing NOAA NCDS MaritimeChartService WMS GetMap endpoint, with WMS 1.3.0, `CRS=EPSG:3857`, layer IDs 0–12, transparent 256×256 PNG and Web Mercator tile bounding box. The bbox is computed directly from z/x/y and uses XYZ top-down y, not MBTiles TMS. A valid successful PNG is atomically written with 0700 directories and 0600 file permissions and returned; unsupported upstream content/errors return HTTP 503 with no-store and a retry advisory. Tile bytes are capped at 4 MiB, PNG dimensions checked; malformed/non-PNG data never cached. GO upstream client has a five-second timeout, four concurrent request slots, response-header time limit and bounded idle connections. Simultaneous identical misses are coalesced through shared per-tile flights; an upstream failure opens a 30-second in-process cooldown preventing retries during a NOAA outage. The handler uses an independent five-second context so a disconnected browser cannot leave an abandoned tile flight hanging indefinitely; bounded and non-blocking selection protects the server. Successful cached tiles remain available while the circuit is in cooldown. Go only fetches on demand; **no background downloader, automatic scheduled refresh, eviction, cache invalidation or bulk offline coverage** has been added.

Path and method validation remain before I/O; bad methods 405, invalid coords 400, corrupt or inaccessible cached content 503, upstream failure 503, successful cached/fetched PNG 200 with a bounded browser private cache. Source provenance and chart timestamp/freshness are not shown per tile and thus this implementation must not imply current navigation suitability. The previously downloaded `ncds_19c.mbtiles` is still not directly supported; no old chart package silently used. The original all-error/12-second fallback and single Loading+Cancel / Failure+Close UI remain, though a fast upstream 503 may trigger the failure before the 12-second timer. Safari never needs to learn NOAA URLs or fall back directly to NOAA. Live NOAA WMS compatibility still requires owner Mac/Safari and real-service verification, distinct from offline CI mocks.

### Nautical tile observable diagnostic contract — Issue #37

Every Go nautical endpoint response now carries `X-Sailing-Chart-Source` with one of `cache`, `noaa`, `unavailable`, plus `X-Sailing-Chart-Result`: `cache-hit`, `noaa-fetched`, `noaa-fetched-shared`, `noaa-timeout`, `noaa-http-error`, `noaa-invalid-png`, `noaa-request-error`, `noaa-error`, `queue-timeout`, `cooldown`, `cache-unavailable`, `cache-invalid`, `cache-read-error`, `cache-write-error`, `invalid-method` or `invalid-coordinates`. `X-Sailing-Chart-Upstream-Status` is supplied only when a real upstream HTTP response supplied a nonzero status; cooldown and connection timeouts do not invent one. Successful disk hits return `cache/cache-hit` and never call NOAA. Failed ongoing coalesced misses preserve the original attempt's result. Only the actual outbound function emits a compact `NAUTICAL tile=z/x/y upstream=noaa result=... status=... duration_ms=...` log event, without secrets, URL/query, disk paths or response content; 503 from cache/cooldown alone does not imply an outbound attempt. Diagnostic metadata are low-cardinality and do not alter API status codes, user account privacy, HTTP connection semantics, tile caching, timeout or UI fallback.

### Nautical progress timers and stale callback exclusion (current draft)

Browser nautical loading has two distinct timers: `nauticalProgressTimer` (200 ms threshold before revealing the status panel) and `nauticalCheckTimer` (12-second normal / 2.5-second explicit loopback-mock safety bound). `nauticalLoadGeneration` and `nauticalRequestZoom` identify the currently relevant request window. `stopNauticalWaiting()` invalidates its generation, clears **both** timers, clears request zoom, and resets `nauticalLoading`; Leaflet `load` normally calls it when the current batch settles. Delayed progress and timeout callbacks check their captured generation; a fast load that finished before 200 ms cannot later display progress. On a new tile `loading` event with a changed zoom, the pending prior window is invalidated and restarted. The status panel never controls nautical tile-layer visibility. This is browser-only: it does not change the NOAA WMS proxy/cache or whether all tiles have chart detail.

### Current-viewport XYZ coverage on pan (latest Stage A)

The older `nauticalSuccessfulZooms[z]` history was insufficient: a successful Pittsburg tile suppressed error detection after an unrelated same-zoom pan far outside generated mock coverage. It is replaced by `nauticalSuccessfulTiles["z/x/y"]`, populated on Leaflet `tileload` using the event's actual coordinates, and cleared for tile-specific `tileerror`. `nauticalVisibleTileRange()` obtains the visible geographic bounds, projects northwest/southeast to `min(map.getZoom(), nauticalLayer.options.maxNativeZoom)`, converts to the Leaflet grid's tile size, and clamps XYZ indices. `nauticalViewportHasTiles()` tests for at least one successful XYZ cell in the **current** viewport. This is a minimum evidence-of-coverage check; it does not prove every chart pixel contains navigational detail.

`nauticalViewportKey()` identifies the requested tile rectangle, including its native zoom. Timed callbacks cannot claim results after moving to a different requested rectangle; the same 200 ms progress threshold and safety timer remain. Leaflet `load` checks visible coverage, not any old success at the same zoom. `map.moveend` calls `checkNauticalViewportAfterMove()` to handle a pan where no new `loading` event fires. The existing single status panel now shows an area-specific panning/zooming suggestion when there are no successful visible cells, including local mock inspection; explicit Cancel alone may select Street. A covered pan restores the unobstructed map. The Go NOAA tile gateway/cache and mock generator are unchanged.
