# Mauri's Weather & Water Conditions — architecture contract

This documents current boundaries and non-negotiable behavior, **not** a requirement to reorganize the sailing source like ScraperGo. Inspect actual code and call sites before modifying a contract.

## Runtime and component ownership

The root Go service includes `main.go` (routing/report preparation), `ui_templates.go` (the four embedded Go HTML template bindings), `web/templates/*.html` (browser UI HTML/CSS/JavaScript), `wind.go`, `currents.go`, and related sources. Go `embed.FS` includes the standalone templates in the compiled binary; the root `go.mod` requires at least Go 1.16. Do not confuse the root-owned `web/templates` with the separate `ui/` Go module. Build the full root package. The repository also contains `cmd/marineplacesgen.go`, supporting assets/scripts, and a separate `ui/go.mod` module. Root `go test ./...` does not automatically validate the nested module. Test it independently for changes in that module.

The public site at https://weather.themauris.org currently uses a locally running Go server exposed through the owner's Cloudflare Tunnel. Do not change listener/process ownership, launchers, private credentials, or tunnel behavior as an incidental code or theme change.

## Homepage canonical button component

The Homepage-owned nested Go module now also renders one shared suite banner on
Welcome, Conditions Now/Planning, Stations and Details. `ui_templates.go`
embeds its CSS and browser status formatter alongside the existing self-contained
page assets; `/assets/tanner.jpg` serves a local embedded portrait. Every main
panel uses `.suite-content`, which shares the exact viewport width and
responsive gutters with `.suite-banner`. Local page CSS controls vertical
spacing and functional content, not duplicated masthead or panel widths.
Existing `.suite-home-link` presentation and redundant links are removed.

The account client displays only `Signed in as <verified user>` through the
shared formatter. Guest/browser-only state and preference conflict, save or
verification notes appear separately in the content area; role permissions,
bearer lifecycle and account record ownership remain local to SailingGo.

The root application pins `github.com/richard-mauri/homepage/shared/ui`, whose embedded `buttons.css` is included **after** SailingGo's own `web/static/theme.css` in each of the four rendered page templates. The existing server-side template assembly embeds the bytes into the response, with no runtime call to Homepage or changes to CSP. `--text` aliases SailingGo's `--ink`; its existing `--soft`, `--line`, and `--accent` provide the other canonical tokens.

Standard text actions in Conditions Now—Clear location & stations, Clear all overlays, information-popup launchers and Tidal & Lunar Context—use `button.ui-button` and must not reintroduce local appearance/hover/disabled/focus rules. Structural width/alignment styles are allowed. Compact map navigation menus, playback transports, icon-only close actions, station-camera controls and chart interactions are deliberately specialized for their distinct size and context; this is a first-phase adoption, not a blanket restyling. Later phases should review those components deliberately against Homepage's canonical design system.

## Environmental data semantics

**Observed wind** comes from NOAA/NDBC and selected validated NOAA CO-OPS mappings. Show timestamps, source and freshness; station height/exposure matters. Existing documented fallback mappings include PSBC1 (9415115), MZXC1 (9415102), PPXC1 (9414847); do not double-count overlapping samples from different feeds. Automatic nearest-usable wind selection has a documented 30-minute freshness rule; check source before editing.

**Tidal currents** are NOAA **predictions**, not directly observed flow at the boat. Flood, ebb, slack, maxima and current-station selection remain distinct from wind observations and wind-station choice.

**Forecasts and overlays** (marine/point weather, wind barbs, radar, smoke/fire, pressure, temperature, swell and other layers) are separate products with differing coverage, timeliness and provenance. Never present one as another.

## Selection, UI and routes

Clicking a map point selects the sailing location. **Panning, zooming, or Center Map must not change that selected location.** Preserve automatic and explicitly overridden `station=` behavior, while current-station matching stays independent. Preserve Conditions Now and Planning and Details, history charts/tables, units, warnings, responsive layout, overlays, markers and popovers.

Existing documented routes include `/report`, `/planning`, `/wind-readings`, `/wind-stations`, `/point-weather`, `/marine-forecast`, and supported HTML/text/JSON output. The last documented `/wind-readings` fix expects JSON fields `hours`, `readings`, `summary` and windows 1, 4, 8, 12, 16, 20 or 24 hours. Trace handlers and front-end consumers before changing schemas.

## Return to Homepage navigation
SailingGo's browser UI exposes a visible native anchor `<a href="https://home.themauris.org/">← Back to Homepage</a>` with no `target` and no JavaScript history manipulation. It navigates in the current tab and can be used regardless of account sign-in. The link adds no new server endpoints, exposes no credentials, and does not modify app-local state. Homepage PR #12 is merged; all four launcher cards use same-tab navigation.

The suite-wide return button uses the same `.suite-home-link` presentation in all four apps: 38px minimum height, 8px/12px padding, 10px radius, muted border at rest, accent border and darker fill on hover, and a visible keyboard focus outline. Place one link at the upper-left above the primary content/heading.

The shared suite navigation style is now intentionally a quiet 12px text link directly below each page's primary heading, with subtle hover background and underline and keyboard focus outline (rather than the former 38px bordered button). ## Homepage-authenticated automatic preferences (Issue #17)

The embedded `web/static/account.js` runs on Conditions Now and Planning and Details. SailingGo consumes Homepage's URL-fragment `#suite_token`, removes it immediately and retains the transferable bearer only in tab-scoped `sessionStorage`. Explicit `#suite_mode=local` clears it. Identity and expiry come from the trusted `/api/session/profile` bearer validation; no independent SailingGo login exists. The shared banner renders **Signed in as [verified user]** without an app or role suffix. Guest and preference-sync notices appear separately below the banner, with no manual Save/Load controls.

On authenticated startup, SailingGo GETs the revisioned `/api/storage/sailing` account record. Saved settings are applied automatically to the current view, including canonical URL parameters and map settings where the map exists. When an account has no record, its initial preferences are established without requiring a manual sync. Changes are staged in the tab before URL navigation and optimistically PUT with the last server revision; the next page also recovers staged changes if navigation canceled an earlier request. The previously loaded account record, not a stale launch URL or another user's local settings, is authoritative. Conflict (HTTP 409), invalid schema, expiry, loss of network or a new identity must not silently overwrite another account. A conflicting browser change is retained locally and identified in the account-status text. Browser-only visits retain a distinct local browser copy and remain functional.

The preference payload schema remains version 1, with selected URL settings, overlays, map type and marine-place categories. Panning/zooming the map does not become a selected sailing location. The merged Homepage companion provides the trusted origin, storage namespace and handoff; the owner controls Mac/Safari/live-tunnel acceptance for future changes.


## In-place unit changes and account restoration (build v399)

The existing Wind units and Distance units controls now update the browser URL using `history.replaceState` and dispatch a unit-change event; they do **not** set `window.location.href` or destroy the page. The embedded `web/static/unit_refresh.js` fetches the equivalent server-rendered document and updates static display text and wind metrics in place, preserving the Leaflet map and bound UI handlers. Wind history uses its existing JSON refresh path to recalculate the chart/table in the selected units. Dynamic map and chart controllers are never replaced. A failed fetch rolls the selector and URL back to the previously rendered units rather than leaving misleading values visible.

The account client applies *unit-only* saved preference differences using the same in-place mechanism, not `location.replace`. A brief bounded initialization mask on the unit-dependent controls/data prevents showing stale units while the authenticated Homepage storage read is pending. Selected station/location changes may still require server-side navigation, as they alter underlying report context. Authentication and user-data isolation are unchanged. Verify all dynamic map overlays, wind/history time ranges and unit-sensitive calculations in Safari before merge.

## Direct-visit recovery (Issue #19)

On the public `weather.themauris.org` origin only, if the embedded account client has no cached bearer and was not explicitly launched with `#suite_mode=local`, it redirects once to Homepage's exact fixed `/launch/sailing` route. Homepage runs a same-origin POST against the existing parent session and returns only a child bearer in `#suite_token` or explicit `#suite_mode=local` when no valid session exists. SailingGo clears the fragment, retains bearer only in tab-scoped sessionStorage, and performs the same validated profile+revisioned account sync as normal handoff. Explicit browser-only mode suppresses recovery, avoiding redirect loops. A direct visit when Homepage's bridge has a network error stays on its recovery error page with a manual local-mode link; it does not forge sign-in. No changes to authenticated user isolation, session lifetime, automatic preference saves or NOAA/dashboard semantics. The companion Homepage direct-visit bridge is merged.

## Optional Homepage activity telemetry (Issue #21, merged; verified identity in Issue #23)

`activity.go` contains a strictly optional, server-only `ActivityReporter`. Environment variables `SAILING_ACTIVITY_URL` and `HOMEPAGE_ACTIVITY_KEY_SAILING` jointly enable it; if disabled, embedded templates receive no new `activity.js` reference. The existing `ui_templates.go` embedding pipeline inserts a defer-loaded script only when the private configuration validates. Browser-generated random tab IDs stay in same-origin tab `sessionStorage` and are submitted to SailingGo's own strict-origin `POST /api/activity/ping`. The reporter bounds presence to 5,000 entries, throttles repeated IDs and computes rolling windows in memory. A server-only no-redirect request submits aggregate data to Homepage `POST /api/admin/activity/ingest` as `sailing`, with an explicit service bearer, timestamp and nonce, once a minute. No coordinates, NOAA data, user IDs, station names or per-tab identifiers leave SailingGo.

Issue #23 adds server-side verification of the existing Homepage child bearer before marking activity signed in. The trusted Homepage profile endpoint returns origin-scoped pseudonymous session/user aliases, enabling per-session deduplication across tabs and private per-user presence summaries without putting aliases or bearers into collector reports. Rejected supplied identity gets a 401 response; Homepage verification outage gets 503. The embedded account client recognizes Homepage's one-hour `guest` role without attempting account storage, and shows a non-dismissible sign-in dialog with a manual Homepage action for invalid/expired/explicit local sessions. Named settings and URL/viewport rules are unchanged.

In `main.go`, server request middleware measures the concurrent lifetime of rendered reports and weather/map API requests, excluding health and static assets. `prefetchSwellRaw` separately increments the same in-flight count only once its bounded prefetch slot is acquired. This is a snapshot of observed work, not every upstream goroutine in the service. No changes are made to NOAA observation/prediction semantics, location/viewport separation, HTML/text/JSON response formats, authentication or page preferences. The optional `SAILING_ACTIVITY_TEST_LISTEN=127.0.0.1:8087` forces only an explicitly requested local test instance onto loopback; the existing production listener default is otherwise unchanged. Issue #23 implemented server-side Homepage verification of named/guest activity, with per-session deduplication; invalid bearer returns 401 and temporary verification outage 503.

## Homepage-verified suite access candidate — Issue #35 (not yet wired)

`sailing_suite_auth.go` stages an independent per-request verifier using the immutable-pinned Homepage `shared/auth` module already consumed by NewsGo and ScraperGo. It checks strict 64-digit lowercase-hex `Authorization: Bearer` credentials against the fixed Homepage HTTPS `/api/session/profile` endpoint with SailingGo's trusted `Origin`, a bounded four-second client, no redirects and an 8192-byte JSON cap. Rejected/expired identities receive HTTP 401, provider/network failure HTTP 503, and only verified user/admin/Guest roles are valid. The `ProtectAPI` middleware supports all `/api` and `/api/*` paths, including unknown future routes, and sets `Cache-Control: no-store`.

**Important integration boundary:** The middleware is intentionally **not installed** in `main.go` yet. SailingGo has non-`/api` weather, overlay and report routes as well as HTML navigations that do not automatically attach bearer headers. These must be inventoried and migrated alongside the browser account/handoff client before making the listener fail closed. Existing access remains unchanged in this phase. No authenticated safety claim may be made until the listener and every data route are protected, regression-tested and accepted in Safari. NOAA observed wind, predicted tidal currents, map click versus pan and account preference isolation remain untouched.

## Explicit user-initiated preferences — draft PR #36

The earlier automatic 250 ms Homepage preference writer and 1.2 s retry timer in `web/static/account.js` are replaced with a single user-triggered `flush()` handler on the **Save Changes** button in the two report views. `stage()` writes a revision-scoped personal draft to the existing tab sessionStorage `sailing.preferences.pending-account.v2`; `stageGuest()` writes the Guest draft to `sailing.preferences.pending-guest.v1` (also tab sessionStorage). Neither stage function commits to Homepage or the browser's saved local preference record. Pending preferences are applied on navigation/restoration and only saved upon button activation. The Guest commit writes `sailing.preferences.browser.v2`, and the personal commit issues one revision-checked `PUT /api/storage/sailing`. Conflicts retain changes and block overwrite; other failures leave pending edits available for manual retry. A `beforeunload` prompt protects unsaved edits, excluding internal account-preference restore navigation which preserves the pending draft. Guest profile verification and per-user account isolation are unchanged. The common Homepage account record retains schema version 1 and the existing URL/map/overlay properties. The staged `SailingSuiteGate` remains unwired: this is persistence/UI work, not a claim of completed weather API authorization.

### Net-change detection and explicit discard — Build v429

The dashboard tracks `savedSnapshot`, a deep copy of the last successfully committed account/browser preferences. `same()` compares normalized preference maps regardless of object key insertion order. Each personal or Guest edit first checks `refreshDirty()`: if the new state equals the saved snapshot it removes its tab-scoped pending draft and clears the dirty flag, even if the user previously changed the map type or overlays. A shared `ui-button` **Discard Changes** control is installed alongside **Save Changes** on the two report views; it clears pending drafts and the blocked conflict state, then reapplies the saved snapshot. Discard issues no Homepage PUT and does not update Guest browser-local persistence. A successful Save replaces the snapshot; a failed/409 Save leaves the draft intact. The beforeunload warning depends on net unsaved differences, not the number of change events. This behavior does not change the still-unwired security gate, NOAA, or account ownership.

### Map Type capture event ordering (Build v430)

The account preference `change` handler runs in the capture phase, before the existing map controller's radio listener calls `setBaseMapLayer()` and `history.replaceState()`. Previously `settingsFromPage()` could pair the newly selected `mapType` with the **previous** `map_layer` URL value, causing false dirty state after Street → Nautical → Street. The account listener now explicitly sets `next.mapType` and the matching `next.params.map_layer` from `target.value` for `input[name='map-type']`, deleting `map_layer` for Street. The original map controller retains exclusive responsibility for map/URL presentation. The regression in `scripts/test-explicit-save.cjs` executes the actual account event handler against a URL intentionally lagging behind the radio selection, for both personal and Guest sessions. No change to NOAA routes, map zoom restrictions, location selection or account record schema.

### Canonical saved/current preference comparison (Build v431)

`canonicalState()` makes preference equivalence independent of sparse historical records: an absent overlay or marine-place category is treated as unchecked (`false`), while the map radio type is the authority for `map_layer` rather than a lagging query string. `same()` compares canonical copies without mutating the saved record, current draft or schema sent to Homepage. The real capture-handler regression includes visible checked and unchecked overlay/category controls and verifies Street → Nautical → Street, then an actual overlay toggle and reversal, for both personal and Guest sessions. This is comparison-only; no automatic writes or server schema changes.

### Incremental state changes (Build v432)

The captured preference event now starts from the tab's pending settings or `savedSnapshot`, and modifies **only** the changed control: map type and its URL layer pair, wind/distance/history units, one overlay checkbox or one marine-place category. `settingsFromPage()` is reserved for initial state creation; it is not used to reconstruct every event from incidental map viewport URL parameters and controls. Canonical comparison also resolves an older `mapType:""` to Street unless its stored `map_layer` explicitly names Nautical, Satellite or Hybrid. Regression covers a stale URL containing a separate map-center field and legacy empty map type. No change to the persisted schema or explicit-save authorization boundaries.

### Tidal-current range and explicit Save (Build v433)

The `#current-days-picker` control changes `current_days` through an in-place fetch and `history.pushState()`, not an account-client full-page navigation. Its capturing `change` event now stages exactly that property before the chart is replaced. Choices 3 and 7 are stored as strings; returning to the default 1 day removes the optional property. Canonical equality also treats legacy `current_days:"1"` as absent. The account/Guest persistence remains explicit-button-only, and the chart loader still owns its own fetch and URL update.

### Complete report select and checkbox persistence (Build v434)

The report template has seven `select` controls and 23 checkboxes (14 environmental/map toggles including ALERTCalifornia, eight marine-place category toggles, and one tidal-current daily-range overlay). Map Type has four radio choices handled separately by the existing map state. The account client now inventories all seven selectors and 23 checkboxes in CI. Previously uncovered controls were `map-swell-playback-speed`, `map-swell-playback-step`, `map-alertcalifornia-mode`, `map-show-alertcalifornia` and `show-tide-range-overlay`. These are captured into the existing revisioned schema-1 settings record through explicit state deltas. Select-only UI preferences use allowlisted `params` keys `swell_playback_speed`, `swell_playback_step` and `alertcalifornia_mode`; they are deliberately excluded from report URL rewriting and normalized against defaults during comparison. The ALERTCalifornia visibility checkbox is a map overlay, while the daily tidal-range overlay checkbox is a display overlay whose missing legacy setting means checked by default. Restoring UI-only selections dispatches native change events with account staging suppressed, so the original map transport/camera controllers update their internal state without automatic preference persistence. The tidal chart replaces its subtree via AJAX; a `sailing-current-chart-updated` event causes the account client to restore the saved or pending checkbox state after replacement. The dates, current-station selection, and underlying observed/predicted data semantics remain unchanged. The still-unwired access gate is unaffected.

### Wind History and preferred-period planning state (Build v435)

The preference model already allowlisted `wind_hours`, `planning_start`, `planning_end`, `caution_ebb`, `caution_flood`, `max_ebb`, `max_flood`, `planning_buffer`, and `current_distance_warning` as URL-derived schema-1 values. However, the capture listener did not track the eight time/number planning controls, while wind history could treat its default 4-hour selection as dirty relative to a missing/default saved value. The listener now stages an incremental, validated update for each planning control using its existing URL key (no new schema or account endpoint). Canonical equality treats `wind_hours=4` and omission as equivalent, as with the established current-days default. Planning values are normalized to the existing controller's default/time/precision conventions (12:00–17:00, 2.0 kt caution, 3.0 kt red, 60-minute buffer, 15.0 nmi distance); a reversal to the saved value clears pending changes. The current-chart subtree is replaced by the chart's in-place AJAX fetch: on `sailing-current-chart-updated`, planning input values are reapplied from the authenticated user's or Guest's current pending/saved state without firing another change event or second fetch. The chart controller retains ownership of recomputation; the account client retains ownership of persistence. No NOAA semantics, security guard integration or listener changes.

## Current server authorization boundary — Build v436 draft

The previously staged SailingSuiteGate is now wired into the production Go listener. main.go constructs NewSailingHTTPAuth(NewSailingSuiteGate()) and wraps the final router with authGate.ProtectWeather(handler) before http.ListenAndServe. The full router is default-deny, except the narrow public allowlist: health, welcome, activity.js, hero/tanner images and favicons. Report HTML/text/JSON, planning, wind, current, weather, all environmental overlays, marine-places JSON, API and unknown routes are protected. Each request verifies the authorized Homepage profile. Missing/revoked/expired identity is denied (401), and Homepage network/profile failures return 503. Spoofed identity headers and unverified local mode never authorize.

Since browser navigation cannot supply Authorization headers, anonymous top-level HTML requests receive a no-data, no-store entry page that consumes Homepage's suite_token fragment, erases it from the URL, and POSTs to /suite/session with same-origin verification. The server creates a first-party Secure HttpOnly SameSite=Lax __Host-sailing-session cookie containing an AES-GCM encrypted token plus expiry. The encryption key is generated at process startup; restart invalidates old cookies. Cookie-authenticated writes require same origin. The server still revalidates every weather/API request rather than trusting the cookie alone. Local loopback uses a separate non-Secure browser cookie name for development, but cannot bypass Homepage verification. An explicit Authorization Bearer header is also supported for CLI clients. AJAX chart refreshes receive 401 rather than a sign-in HTML body on authorization failures. User/admin and verified Guest are allowed for application use; Guest settings remain browser-local and Homepage isolates personal settings by user. Earlier notes about an unwired gate describe older builds, not v436. CI mocks are not real Safari or tunnel verification.

### No-flash sign-in and chart refresh (Build v437)

The intentionally minimal `sailingEntryHTML` supplied for anonymous top-level HTML now embeds the same `color-scheme:light dark` and `--bg`, `--panel`, `--ink` values used by `web/static/theme.css`; both `html` and `body` paint the proper surface immediately during Homepage cookie exchange. This remains a data-free authentication entry point, not an unguarded weather page. On the report, `loadCurrentURL` is the existing in-place fetch pathway for `current-days-picker`, date navigation and all eight planning controls. The prior `.current-refreshing{opacity:.55}` dimmed multiple large report cards and created a visible global flash; the new controller retains full opacity, marks only the chart as `aria-busy`, and presents an inline status. On HTTP/fetch/invalid response failures, it preserves the existing cards and URL and displays a recoverable message instead of `window.location.assign`, which would reload and risk disrupting explicit pending preferences. The saved/pending state and chart restoration events remain unchanged. CI tests assert the no-reload failure path and shared entry palette; production Safari/NOAA remains unverified.

### Stable preferences toolbar layout (Build v438)

In `web/static/account.js`, the dynamically inserted `#sailing-save-status` was formerly appended to the `.page-preferences` flex row together with the Save/Discard buttons. The status length varied among unsaved, saving, conflict, saved and empty messages, changing flex distribution/line wrapping and visibly shifting controls. The account script now appends only the buttons to the toolbar and inserts the ARIA live-region status **after** the toolbar as its own block element. Embedded `web/static/theme.css` defines a full-width, permanently reserved minimum-height status line with 0.75rem text, right alignment on desktop and left alignment on narrow screens. No account state, persistence, event handlers or security behavior changes. Go source/embedded-style regression tests enforce the separation; Safari confirmation remains pending.
